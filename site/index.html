.NET 11

Built on .NET 11, ready for your .NET 11 code

Passenger runs on its own copy of .NET 11, carried inside it, and reads what .NET 11 and C# 15 bring to your code in the editor, the debugger and the profiler. Your projects can target .NET 8 or later.

Runtime async, stepped as written

Code compiled with .NET 11's runtime async debugs as you wrote it: Step Over an await stops on the method's next line once it goes on, whichever thread it goes on, and Step Out stops in the caller that awaited it, showing the value the method returned.

C# 15, read as C# 15

A union is coloured as you declare it, and a collection expression's with(…) arguments build with no preview error. In the debugger a union shows the value it holds, as that value's own type.

Measured from its first moment

Live metrics, the Requests window and your agent's telemetry read a .NET 11 program from its start, where an older one is first left a few seconds, and a memory snapshot reads a .NET 11 program's heap.

Web apps on the new SDK

Under Hot Reload a debugged web app's open pages follow your edits through the .NET 11 SDK's browser refresh, as through the older SDKs', and the Migrations window runs EF Core 11's dotnet ef with the defaults your .config/dotnet-ef.json names.

Several frameworks, one project

A project built for .NET 10 and .NET 11 runs its tests under each, every framework's results shown apart, and project files complete net11.0 and C# 15's LangVersion.

The SDK when you need it

Open a .NET 11 project on a machine without its SDK and Passenger says so and offers to install it into your own folder, used at once by Passenger, its terminal and what it starts.

Godot

Godot 4: your scenes and the running game, in your code

For games in C#, in GDScript or in both. Passenger checks your code against your scenes, debugs both languages at once, and works beside Godot's editor or as its script editor.

C# that knows its scenes

GetNode<T> paths and types, res:// paths, [Export] values, signals and every string Godot takes (input actions, groups, animations, autoloads) complete and are checked against the scenes that run the script. A rename reaches the scenes, and a scene is marked where Godot would not load it, with fixes.

Godot in depth

GDScript and shaders, as Godot reads them

Passenger's port of Godot's parser and analyzer gives Godot's own warnings and errors with their fixes, completion, the hover, Find Usages and Rename, mostly without starting Godot. Shaders are checked as Godot's compiler checks them, every error and warning at once.

Both languages, one debugger

A breakpoint in C# or GDScript stops the game, a script you save reloads in it, and Godot's types read as you think of them in Variables.

The running game, tuned

Its nodes and values in the Live Visual Tree, changed while it plays and kept into the scene, a node picked by clicking in the game.

One profile, both languages

GDScript's functions and Godot's frame times beside the C# in one call tree, a slow frame opened on what it spent.

Its tests

GdUnit4 (its engine tests on Godot 4.7), GUT and GoDotTest tests found, run and debugged in the Unit Tests window.

Beside Godot's editor

Passenger becomes Godot's script editor in one step, and its addon has a game Godot's Play starts debugged in Passenger.

The game in a pane

On Windows, macOS and Linux under X11, the game can draw beside its code, taking the keys when you click it.

Debugger

Fix bugs while the program runs

Passenger's own debugger, over ICorDebug and .NET's browser debug proxy, works the same on your machine, inside a container and in the browser.

A debugger of its own

Breakpoints with conditions, hit counts and log messages, Smart Step Into, the values methods returned (an async method's too), Run to Cursor and Set Next Statement, and the values each line used drawn after it. Several programs debug at once, a tab each, and a library without symbols shows its code, decompiled.

Attach to a .NET program already running, in a container too, and on a Mac with nothing to set up.

Hot Reload while debugging

Edit the code, paused or running, and Hot Reload puts it in the program. An edit it can't apply is listed with why, and by default the program restarts to take it.

Blazor, in the browser too

Debug a Blazor Web App and its server stops in one tab while its WebAssembly components stop in the browser in the tab beside it: breakpoints, stepping, Variables, watches and the hover card, under Aspire and in containers too.

With Hot Reload a component's edit shows at once and a saved stylesheet applies in place, the page kept up. The page opens in Chrome, Edge, Chromium or Brave, on a profile of Passenger's own.

Profiler

See where the time and memory go

A profiler of Passenger's own, over the runtime's EventPipe, for a program you run, one already running, or a service in its container.

Where the time goes

Sampling from a program's first instruction or attached to one already running: its call tree, hot spots, flame graph, allocations and garbage collections, narrowed to any stretch of the timeline.

What holds the memory

A memory snapshot counts the heap by type, with each object's retained size, and shows the shortest paths that keep it alive. Two snapshots compared say which objects are new, which died and which survived.

XAML

See your XAML as you write it, and as it runs

Passenger is built with Avalonia, and it gives XAML the help C# gets, from the project's own assemblies and the framework's own compiler and previewer, for Avalonia and WPF alike.

XAML as you type

Completion of controls, properties, values, resources, selectors and binding paths, checked against x:DataType or WPF's design-time data context, the XAML compiler's errors on their lines, and a missing property, command or converter made from where it is used. A rename reaches across C# and XAML, either way.

XAML Preview draws the file beside it as you type (WPF's on Windows), and the XAML workspace sets the file, its preview and the running app's tree side by side, one selection across the three.

The running app, from its XAML

Debug an Avalonia app, or a WPF app on Windows, and the Live Visual Tree shows its controls as they are, each property with where its value came from and each style with why it applies or not. In Avalonia the XAML shows each binding's value after its line, and a breakpoint goes on an element.

Save a XAML file and XAML Hot Reload puts it in the running Avalonia or WPF app. A binding that fails is a row in Problems with a fix, and can stop the debugger like an exception.

Agents

A coding agent that uses the IDE and tries the app

Passenger is an MCP server. Through it an agent works in the IDE, not only in your files: it asks the language server instead of guessing from the text, and checks what it changed by building, testing and running it. It works with Claude Code, Codex, OpenCode and any MCP agent.

It tries what it builds

When the program is an Avalonia app, a Godot game, or a WPF app on Windows, the agent sees it as a person testing it would: a picture of each window or frame, the tree of its controls or nodes, and clicks, typing and keys, which never take your focus or move your pointer.

It works as you do

It finds where things are declared and used, renames, fixes and formats as the IDE does, builds, runs and tests, debugs and profiles, starts a compose service or an Aspire resource, and changes scenes in your Godot editor, each change one step of Godot's Undo. On your own window it asks you first.

Containers and Aspire

Debug Docker Compose and Aspire services

Passenger runs an app made of several services as one. Your compose files, Dockerfiles and Aspire AppHosts are run configurations as the solution opens, and every .NET service in them runs under Passenger's debugger, Hot Reload and profiler, wherever it runs.

Every service under the debugger

Debug holds each .NET service at its start, attaches inside its container and lets it go, so a breakpoint in Main stops. Each service gets a Debug tab with its log as its console, and Hot Reload reaches them all. A code change needs no image rebuild, and Rerun restarts only the services whose build changed.

Aspire's IDE

Run or debug an AppHost and Aspire asks Passenger to start each project. The Aspire window shows its resources, their consoles, logs and traces, charts each one's metrics and draws the AppHost as a graph, and its code help checks every connection string against the AppHost.

Containers and Aspire in depth

One service at a time

From a service's row, or the run icon beside it in the compose file: debug it, attach to it, restart or profile it in its container while the others run on.

The Containers window

Compose projects and their services, containers, images, volumes and networks: logs, stats, files, details and a shell.

Compose files, understood

Each ${VAR} shown as it comes out, names completed, renamed and checked, and a connection string a service never gets warned of, with its fix.

Images published and checked

Publish ships the SDK's container image, several tags and platforms, to your registry. An image's known vulnerabilities show through your own Docker Scout, when you ask.

Your engine, as it is

Docker Desktop, Colima, OrbStack, Rancher Desktop, Podman or a remote engine, through your own docker command.

Nothing left behind

Stop, closing the folder or a crash takes down what a run started. Your own containers are never touched without asking.

Web apps and their data

See every request your app serves, with its SQL

For ASP.NET Core and EF Core: what your app serves and what it asks of the database, as it runs, with no change to the app.

Live requests and their queries

The Requests window lists each request a running app serves, and the database commands it ran, with their times and rows. A command run again for every row (an N+1) or a slow one is marked; a request opens at its handler, or at the exception that ended it. It works for Run, Debug and Profile, and for the services of a compose run or an AppHost.

EF Core migrations that run

The Migrations window lists each context's migrations and whether the database has them: add, remove, update, script and bundle. Before dotnet ef runs it finds what would stop it (the tool missing or of another version, the Design package, a provider behind) and offers the fix. During a compose run or an AppHost, it works on the database that run uses.

Endpoints from your code

Minimal APIs, controllers, Razor Pages, Blazor, SignalR and gRPC routes read from the code with no build, each sent to the running app from its icon. An app's OpenAPI document becomes requests, each response checked against it.

Logs, traces and settings

Turn on Collect logs and traces and a project's run shows its OpenTelemetry logs and traces beside its console. appsettings.json and user secrets complete the keys your code reads, and a stopped EF Core query shows its SQL in the debugger.

The rest

Everything else a full .NET IDE has

Passenger is .NET from the window to the debugger, over the libraries a C# IDE needs: Roslyn, MSBuild, ICorDebug, EventPipe, VSTest and Microsoft.Testing.Platform.

Coming from Visual Studio? Visual Studio's keys are the default, chords included. Coming from VS Code or IntelliJ IDEA, choose its keymap in Settings.

A full .NET IDE on the Mac. Visual Studio for Mac was retired in August 2024. Passenger runs natively on Apple Silicon, and its debugger attaches with nothing to set up.

The editor and C#

A text control of its own over an immutable rope: multiple carets, folding, soft wrap, live, postfix and surround templates, inlay hints, and splits and tabs in windows of their own. A key costs what it changed, not the file's size.

C# comes from Roslyn: diagnostics, completion, signature help, quick fixes and refactorings such as Change Signature, Extract Interface, Move and Safe Delete, Go to Declaration, Implementation and Base Symbols, Find Usages, hierarchies and decompiled library sources. Problems lists the whole solution's without a build, and Razor and Blazor files get C# and HTML help together.

Git

The Commit window with its changes, the log with its branch graph and branches, side-by-side diffs with the changed words marked, blame, change bars in the gutter that roll a change back, the history of a file, a folder or a selection, stashes, push, pull and fetch, conflicts resolved in a three-way merge, and commits signed with SSH, GPG or X.509.

Show Usages

Every use of the symbol at the caret in a popup over the code, its own file's first, each with its line, a C# member's uses in XAML among them. Choose one to go there, or keep them all in the Find window. A click with a modifier, or a mouse button of its own, runs any action you bind to it.

Questions

Is it really free? What's the catch?

It is free and open source under the MIT licence, for work and personal projects alike, with no paid edition, no trial and no account. There is no catch to find in the code: it is all on GitHub, and the notices list every package and asset it carries, each with its licence: two Microsoft assemblies inside Roslyn's server aren't open source.

Is it ready for daily work?

Passenger is young (0.3.3), and its own development runs through it every day: the coding agents that write much of it work through its MCP server. Its tests drive the whole IDE, a window with real keys and clicks, on macOS, Windows and Linux, and each release is tried on a standing set of real Godot projects. Each release's notes say what it does and its known limits, so you can judge for your own projects.

Which systems and projects does it run on?

Windows (x64 and Arm64), macOS on Apple Silicon, and Linux (x64 and Arm64), with a .NET SDK from 8 for your projects. It works with modern .NET (CoreCLR): console, ASP.NET Core, Blazor, Avalonia and WPF projects, Godot 4 games in C# and GDScript, and the services of a compose file or an Aspire AppHost. .NET Framework, Mono and Unity aren't Passenger's.

Which Godot does it need?

Any Godot 4 for GDScript, and Godot's .NET build for C#, found from GODOT, the PATH or your applications, or named in Settings. The Game window takes Godot 4.4 or newer (4.5 or newer on macOS). The Godot page says the rest.

Does it need an account or send data?

No account, no sign-in and no telemetry. Passenger reaches the network only for what you use (your package feeds, a JSON file's schema, a Dockerfile's base image) and once a day to ask GitHub whether a newer release is out, sending nothing but its version, which Settings can turn off.

How are bugs reported and fixed?

In GitHub's issues: say what you did, what you expected and what happened, with the log (Help, Show Log). Fixes land on main and ship in the next release's notes.

Can my coding agent use it?

Yes: Passenger is an MCP server for Claude Code, Codex, OpenCode and any agent that can add one. Set it up in a minute.

How to install on Linux

Passenger needs:

  • A .NET SDK for the projects you open, .NET 8 or later. It builds and runs them with it; without one, it says what is missing and installs one in a step once you agree. Its own language server, project host and debugger run on the .NET it carries, whatever the machine has.
  • Git, for version control.
  • Node.js, for JavaScript, TypeScript, HTML, CSS, JSON, Dockerfiles and YAML: 22.22.2 or later for TypeScript. C#, XAML, GDScript and shaders do without it.
  • Godot 4, for Godot games (its .NET build for C#), found from GODOT, the PATH or your applications, or named in Settings.
  • Chrome, Edge or another Chromium browser, for debugging Blazor's WebAssembly.
  • A container engine running Linux containers (Docker Desktop, Colima, OrbStack, Rancher Desktop, Podman or a remote engine), only for compose files, Dockerfiles and an AppHost's containers.

Every release, with its notes and its SHA256SUMS, is on GitHub.
