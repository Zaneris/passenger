Containers and Aspire

Debug Docker Compose and Aspire services

Passenger runs an app made of several services as one. Your compose files, Dockerfiles and Aspire AppHosts are run configurations as the solution opens, and every .NET service in them runs under Passenger's debugger, Hot Reload and profiler, wherever it runs.

Every service under the debugger

Debug holds each .NET service at its start, attaches inside its container and lets it go, so a breakpoint in Main stops. Each service gets a Debug tab with its log as its console, and Hot Reload reaches them all.

By default Passenger builds the services itself and runs each from its build, so a code change needs no image rebuild, and Rerun restarts only the services whose build changed.

Aspire's IDE

Run or debug an AppHost and Aspire asks Passenger to start each project: the Aspire window shows its resources, their consoles, details, logs and traces, and its code help checks every connection string against the AppHost.

Containers and Aspire in depth

One service at a time

From a service's row, or the run icon beside it in the compose file: debug it, attach to it, restart or profile it while the others run on.

Profiled in its container

CPU traces and memory snapshots taken where the service runs and shown as any others, hot spots at their lines.

The Containers window

Compose projects and their services, containers, images, volumes and networks: logs, stats, files, details and a shell.

Compose files, understood

Each ${VAR} shown as it comes out, names completed, renamed and checked, and a connection string a service never gets warned of, with its fix.

Your engine, as it is

Docker Desktop, Colima, OrbStack, Rancher Desktop, Podman or a remote engine, through your own docker command.

Nothing left behind

Stop, closing the folder or a crash takes down what a run started. Your own containers are never touched without asking.

Web apps and their data

Every ASP.NET Core request, with its SQL

For ASP.NET Core and EF Core: what your app serves and what it asks of the database, as it runs, with no change to the app.

Live requests and their queries

The Requests window lists each request a running app serves, and the database commands it ran, with their times and rows. A command run again for every row (an N+1) or a slow one is marked; a request opens at its handler, or at the exception that ended it. It works for Run, Debug and Profile, and for the services of a compose run or an AppHost.

EF Core migrations that run

The Migrations window lists each context's migrations and whether the database has them: add, remove, update, script and bundle. Before dotnet ef runs it finds what would stop it (the tool missing or of another version, the Design package, a provider behind) and offers the fix. During a compose run or an AppHost, it works on the database that run uses.

Endpoints from your code

Minimal APIs, controllers, Razor Pages, Blazor, SignalR and gRPC routes read from the code with no build. A route's icon sends its request to the running app, from your .http file.

Configuration it knows

appsettings.json and user secrets complete the keys your code reads. A key nothing gives is warned of where it's read, and a stopped EF Core query shows its SQL in the debugger.

Profiler and debugger

A free .NET profiler and debugger

Both are written for Passenger, over the runtime's own EventPipe and ICorDebug, and both work the same on your machine and inside a container.

Where the time goes

Sampling over EventPipe, from a program's first instruction or attached to one already running: its call tree, hot spots, flame graph, allocations and garbage collections, narrowed to any stretch of the timeline.

What holds the memory

A memory snapshot counts the heap by type, with each object's retained size, and shows the shortest paths that keep it alive. Two snapshots compared say which objects are new, which died and which survived.

A debugger of its own

Breakpoints with conditions, hit counts and log messages, exception breakpoints, stepping through async code, Smart Step Into, the values methods returned, Run to Cursor and Set Next Statement, and the values each line used drawn after it. Several programs debug at once, a tab each, and the hover card opens an object into its members.

A frame in a library without symbols shows its code, decompiled. Attach to a .NET program already running, in a container too, and on a Mac with nothing to set up.

Hot Reload

Edit the code while debugging and Hot Reload puts it in the program, paused or running. An edit it can't apply is listed with why, and by default the program restarts to take it.

Agents

An IDE your coding agent can drive

Passenger is an MCP server. Through it an agent works in the IDE, not only in your files: it asks the language server instead of guessing from the text, and checks what it changed by building, testing and running it. It works with Claude Code, Codex, OpenCode and any MCP agent.

It tries the app it builds

When the program is an Avalonia app, or a WPF app on Windows, the agent sees it as a person testing it would: a picture of each window, the tree of its controls, and clicks, typing and keys sent to the window, which never takes your focus or moves your pointer.

It works as you do

It finds where things are declared and used, renames, fixes and formats as the IDE does, builds, runs and tests, debugs and profiles, starts a compose service or an Aspire resource, reads a web app's requests and their SQL, and runs the migrations. On your own window it asks you first.

XAML

XAML tooling for Avalonia and WPF

Passenger is built with Avalonia, and it gives XAML the help C# gets, from the project's own assemblies and the framework's own compiler and previewer, for Avalonia and WPF alike.

XAML as you type

Completion of controls, properties, values, resources, selectors and binding paths, checked against x:DataType or WPF's design-time data context, the XAML compiler's errors on their lines, Go to Declaration into C#, and a missing property, command or converter made from where it is used. XAML Preview draws the file beside it as you type (WPF's on Windows).

The running app, from its XAML

Debug an Avalonia app, or a WPF app on Windows, and the Live Visual Tree shows its controls as they are, each property with where its value came from and each style with why it applies or not. In Avalonia the XAML shows each binding's value after its line, and a breakpoint goes on an element.

A binding that fails is a console line linked to its XAML and a row in Problems with a fix, and can stop the debugger like an exception. The profiler charts an Avalonia app's frames.

The rest

Everything else a full .NET IDE has

Everything in Passenger is .NET, from the window to the debugger, over the libraries a C# IDE needs: Roslyn, MSBuild, ICorDebug, EventPipe, VSTest and Microsoft.Testing.Platform.

Coming from Visual Studio? Visual Studio's keys are the default, chords included. Coming from VS Code, choose its keymap in Settings.

A full .NET IDE on the Mac. Visual Studio for Mac was retired in August 2024. Passenger runs natively on Apple Silicon, and its debugger attaches with nothing to set up.

The editor and C#

A text control of its own over an immutable rope: multiple carets, folding, soft wrap, live, postfix and surround templates, inlay hints, and splits and tabs in windows of their own. A key costs what it changed, not the file's size.

C# comes from Roslyn: diagnostics, completion, signature help, quick fixes and refactorings such as Change Signature, Extract Interface, Move and Safe Delete, Go to Declaration, Implementation and Base Symbols, Find Usages, hierarchies and decompiled library sources. Problems lists the whole solution's without a build, and Razor and Blazor files get C# and HTML help together.

Git

The Commit window with its changes, the log with its branch graph and branches, side-by-side diffs with the changed words marked, blame, change bars in the gutter that roll a change back, the history of a file, a folder or a selection, stashes, push, pull and fetch, and conflicts resolved in a three-way merge.

Find anything

Search Everywhere, Go to File, Go to Symbol and Find Action. Find and Replace in Files across the solution, a project, a folder or a scope, with a file mask and a preview. Find Usages in a window of its own, Recent Files and Recent Locations, bookmarks and File Structure.

Project files

In a .csproj, .props or .targets: completion of elements, properties, items and their values, and of package ids and versions from your feeds, the version going to Directory.Packages.props under central package management. A property's hover shows its evaluated value and where it was set.

The web languages

JavaScript, TypeScript, HTML, CSS, SCSS, Less, JSON, Dockerfiles and YAML through their language servers: completion, checks, navigation and formatting, TypeScript on the project's own version and JSON against its schema. ESLint's problems show as you type with its fixes, and the project's own Prettier formats on Reformat Code and on save.

Build, run and publish

A Solution view as MSBuild evaluates it, builds with their errors in Problems, run configurations from your launch profiles, consoles whose stack frames link to their lines, and Publish with the SDK's own profiles.

Unit tests

xUnit, NUnit, MSTest and TUnit, through VSTest or Microsoft.Testing.Platform: found from the code before any build, run marks in the gutter, results grouped and filtered, and any test debugged.

NuGet

The feeds your nuget.config names, packages installed, updated and removed per project, central package management, and vulnerable versions marked with the lowest that fixes them.

Terminal

A terminal emulator of its own with a shell per tab, where vim, less and htop run full-screen. A console program can run and be debugged in it.

Tables, images and fonts

Tool windows docked or floating, editor tabs split or in windows of their own, a window for each solution, and New Solution from any template dotnet new has.

Questions

Is it really free? What's the catch?

It is free and open source under the MIT licence, for work and personal projects alike, with no paid edition, no trial and no account. There is no catch to find in the code: it is all on GitHub, and the notices list every package and asset it carries, each under an open-source licence.

Is it ready for daily work?

Passenger is young (0.2.2), and its own development runs through it every day: the coding agents that write much of it work through its MCP server. Its tests drive the whole IDE, a window with real keys and clicks, on macOS, Windows and Linux. Each release's notes say what it does and its known limits, so you can judge for your own projects.

Which systems and projects does it run on?

Windows (x64 and Arm64), macOS on Apple Silicon, and Linux (x64 and Arm64), with a .NET SDK 10 or later. It works with modern .NET (CoreCLR): console, ASP.NET Core, Blazor, Avalonia and WPF projects, and the services of a compose file or an Aspire AppHost. .NET Framework, Mono and Unity aren't Passenger's.

Does it need an account or send data?

No account, no sign-in and no telemetry. Passenger reaches the network only for what you use (your package feeds, a JSON file's schema, a Dockerfile's base image) and once a day to ask GitHub whether a newer release is out, sending nothing but its version, which Settings can turn off.

How are bugs reported and fixed?

In GitHub's issues: say what you did, what you expected and what happened, with the log (Help, Show Log). Fixes land on the branch of the release in progress and ship in its notes.

Can my coding agent use it?

Yes: Passenger is an MCP server for Claude Code, Codex, OpenCode and any agent that can add one. Set it up in a minute.

How to install on Linux

Passenger needs:

  • A .NET SDK, version 10 or later. It builds and runs your projects with it, and its language server, project host and debugger run on it.
  • Git, for version control.
  • Node.js, for JavaScript, TypeScript, HTML, CSS, JSON, Dockerfiles and YAML: 22.22.2 or later for TypeScript. C# and XAML do without it.
  • A container engine running Linux containers (Docker Desktop, Colima, OrbStack, Rancher Desktop or Podman), only for compose files, Dockerfiles and an AppHost's containers.

Every release, with its notes and its SHA256SUMS, is on GitHub.
